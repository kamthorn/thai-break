# แผนปรับปรุงความเร็วภาษาอื่น (Go, TypeScript, PHP, Java)

สถานะ: แก้ครบทั้ง 4 ภาษาและวัดผลแล้ว (2026-10-16) ส่วนตัวเลข "ก่อนแก้" และแผนด้านล่างคงไว้เป็นบันทึก

ต่อจาก [performance.md](performance.md) ซึ่งเร่ง Rust ไปแล้วประมาณ 11 เท่าโดยผลตัดคำไม่เปลี่ยน ที่นี่คือการวัดภาษาอื่นและแผนทำแนวทางเดียวกัน

## ภาษาที่ได้ประโยชน์โดยไม่ต้องแก้โค้ด

Python (pyo3), C FFI และ wasm/Typst เรียกแกน Rust เดียวกัน จึงเร็วขึ้นเมื่อ build ใหม่ตอนออกเวอร์ชัน

- เปิด `regex` feature `perf-dfa` ทำให้ binary ของ native ใหญ่ขึ้นประมาณ 106 KB (1.83 MB เป็น 1.94 MB, +5.8%, strip แล้ว) ใช้เป็นตัวแทนเท่านั้น เครื่องนี้ไม่มี target wasm32 จึงยังไม่ได้วัดขนาดของ `typst/thaibreak.wasm` (ตอนนี้ 1.36 MB) ต้องวัดก่อนปล่อย
- wheel ของ Python สร้างใน CI ต่อแพลตฟอร์ม ต้องรอรอบ release

## วิธีวัด

- ข้อความเดียวกับรอบ Rust: บทความข่าว 1,500 เรื่องจากคลังในเครื่อง (ไม่ได้ commit) ตัดเป็น 3 ชุดย่อยเพื่อให้ PHP วัดไหว
  - A: บทความยาว 200 เรื่อง 1.11M ตัวอักษร
  - B: ท่อนข้อความสั้น 40,000 ชิ้น (เฉลี่ย 23 ตัวอักษร) 0.91M ตัวอักษร
  - C: สุ่ม 20,000 บรรทัด (ข้อความข่าวที่ถูกแก้ ตัวอักษรไทยสุ่ม ปนอังกฤษ ตัวเลข เครื่องหมาย) 0.81M ตัวอักษร
- ตัดคำทีละบรรทัดด้วย tokenizer ค่าเริ่มต้นของแต่ละภาษา `keepWhitespace = false` เวลาคือค่าต่ำสุดของหลายรอบ (Go, TS, Rust 3 รอบ, PHP 1 รอบ, Java 8 รอบ) โปรแกรมวัดเขียนใหม่ให้อยู่ใน /tmp ไม่ได้ commit
- ผลลัพธ์ถูกเขียนลงไฟล์ (token คั่นด้วย `\x1f` บรรทัดละหนึ่งบรรทัดอินพุต) เพื่อเทียบด้วย `cmp`

### ขนาดบรรทัดที่ยาวขึ้น (1.2M ตัวอักษร แบ่งเป็นบรรทัดยาวต่าง ๆ)

| ความยาวบรรทัด | Rust | Go | TS | Java | PHP |
|---|---|---|---|---|---|
| 500 | 6.4M | 0.85M | 1.04M | 1.38M | 0.20M |
| 5,000 | 6.7M | 0.82M | 0.97M | 0.78M | 0.20M |
| 50,000 | 6.7M | 0.83M | 0.87M | 0.16M | 0.19M |
| 400,000 | 6.2M | 0.81M | 0.82M | **0.022M** | 0.19M |

**Java ช้าลงเป็นกำลังสองตามความยาวบรรทัด**: ข้อความ 400,000 ตัวอักษรบรรทัดเดียวใช้ 55 วินาที (Rust 0.19 วินาที) สาเหตุที่น่าจะเป็นคือ `ThaiViterbiTokenizer.java` เรียก `text.substring(runeStart[i])` ทุกตำแหน่ง ซึ่งคัดลอกส่วนท้ายของข้อความทั้งหมด (O(n²)) Rust ใช้ slice ที่ไม่คัดลอก TS ช้าลงเล็กน้อยตามความยาว ส่วน Go และ PHP ไม่ขึ้นกับความยาว ปัญหานี้กระทบฟิลด์เนื้อหายาวใน OpenSearch เช่น เอกสารเต็ม

## คอขวดที่พบ (profile)

| ภาษา | วิธี | สิ่งที่พบ |
|---|---|---|
| Go | pprof | `endsWithInnerFunctionWord`+`bordersFunctionWord` ~29% (สะสม), `TCCPosArray` ~24% (ใช้ `regexp` ซึ่ง Go ไม่มี DFA), `slicerunetostring` ~13% (สร้าง string ต่อ OOV edge), ค้นพจนานุกรม ~7% |
| TypeScript | V8 `--cpu-prof` | `segment` ~58% (self รวมฟังก์ชันที่ inline เข้ามา เช่นตรวจคำหน้าที่, `slice().join()` ต่อ OOV edge, สร้างอ็อบเจ็กต์ edge ต่อตำแหน่ง), GC ~10.5%, `tccPosArray` ~9%, ค้นพจนานุกรม ~11% regex ของ V8 ไม่ใช่ปัญหา (< 3%) |
| PHP | ablation | ปิดการตรวจคำหน้าที่ใน OOV edge แล้ว 5.7 วินาทีเหลือ 2.3 วินาที (**~60% ของเวลาทั้งหมด**) TCC ทั้งหมดใช้ 0.28 วินาที (~5%) เพราะ PCRE JIT เปิดอยู่ ส่วนที่เหลือคือโค้ด PHP ในลูปต่อตำแหน่ง (`preg_match` ทีละตัวอักษรใน `isThai` และ OOV char, `implode(array_slice())` ต่อ edge) |
| Java | อ่านโค้ด | โครงสร้างเดียวกัน (`new String(runes,…)` ต่อ OOV edge, `bordersFunctionWord`, `substring` ต่อตำแหน่ง) ยังไม่ได้ profile ในรอบนี้ |

ทุกภาษามีโครงเดียวกับ Rust ก่อนแก้ (สตริงต่อ edge, สแกนคำหน้าที่ 43 คำต่อ OOV edge, TCC ด้วย regex) จึงใช้บทเรียนเดียวกันได้ โดยไม่ต้องคิดอัลกอริทึมใหม่

## ช่องว่างของ parity ที่มีอยู่ก่อน (พบระหว่างวัด ไม่เกี่ยวกับความเร็ว)

เทียบกับ Rust บนชุดสุ่มเดียวกัน Go, TS ต่างจาก Rust ในบางบรรทัด (Go 1 บรรทัดจาก 200 ในชุด A, 20 จาก 20,000 ในชุด C, TS 3 และ 21) PHP ตรงกับ Rust ทุกบรรทัด สาเหตุที่เจอ:

- ตัวเลขไทย (๐-๙) ปนกับเลขอารบิก: Rust และ PHP นับ `\d` รวมเลขไทย จึงได้ token เดียว (`1๐.๐๐`, `2540๖`) ส่วน Go และ TS ใช้ `\d` แบบ ASCII จึงแยก (`1`, `๐`, `.`, `๐๐`)
- ตัวควบคุม U+0085 (NEL): TS คงไว้เป็น token ส่วน Go และ Rust ตัดทิ้งเหมือนช่องว่าง

เรื่องเหล่านี้ควรเปิดเป็นประเด็นแยกและไม่แก้ในงานความเร็ว เพราะจะเปลี่ยนผลตัดคำ ผลที่ตามมาคือ **การตรวจว่าผลเหมือนเดิมต้องเทียบแต่ละภาษากับผลก่อนแก้ของตัวเอง** ไม่ใช่เทียบกับ Rust

## ผลหลังแก้

ผลตัดคำเหมือนเดิมทุกบรรทัด (เทียบกับผลก่อนแก้ของภาษานั้นเองด้วย `cmp` บนชุด A, B, C) และชุดทดสอบของทุกภาษาผ่าน (`go test`, `npm test`, `phpunit` 114 test, Java 128 test และ `precommit`) วัดด้วยโปรแกรมและข้อความเดียวกับตารางก่อนแก้ ค่าต่ำสุดของหลายรอบ

| ภาษา | A บทความยาว | B ข้อความสั้น | C สุ่ม |
|---|---|---|---|
| PHP | 0.78M (จาก 0.19M, 4.0 เท่า) | 0.68M (จาก 0.18M, 3.7 เท่า) | 0.76M (จาก 0.21M, 3.6 เท่า) |
| Java | 4.07M (จาก 0.49M, 8.3 เท่า) | 3.37M (จาก 1.40M, 2.4 เท่า) | 3.28M (จาก 1.45M, 2.3 เท่า) |
| Go | 3.38M (จาก 0.83M, 4.1 เท่า) | 2.68M (จาก 0.81M, 3.2 เท่า) | 2.78M (จาก 1.01M, 2.7 เท่า) |
| TypeScript | 2.72M (จาก 0.93M, 2.9 เท่า) | 2.22M (จาก 0.94M, 2.4 เท่า) | 2.32M (จาก 1.11M, 2.1 เท่า) |

ขนาดบรรทัดที่ยาวขึ้น (ตัวอักษรต่อวินาที): Java หายช้าเป็นกำลังสอง (บรรทัด 400,000 ตัวอักษรจาก 55.5 วินาที เหลือ 0.33 วินาที, 3.65M/s; บรรทัด 200,000 ตัวอักษรจาก 14.7 วินาที เหลือ 0.18 วินาที) PHP ไม่ขึ้นกับความยาว (0.79M, 0.77M, 0.76M ที่บรรทัด 5,000, 50,000, 200,000) Go ไม่ขึ้นกับความยาว (3.5M, 3.3M ที่ 5,000 และ 200,000) TS ยังช้าลงเมื่อบรรทัดยาวมาก (3.0M ที่ 5,000, 2.0M ที่ 200,000) ยังไม่ได้หาสาเหตุ

เทียบ Rust (6.9M, 5.0M, 5.7M): Java ช้ากว่าประมาณ 1.7 เท่า, Go และ TS ประมาณ 2-2.5 เท่า, PHP ประมาณ 9 เท่า

### สิ่งที่พบระหว่างแก้ (ต่างจากแผนเดิม)

- **PHP:** `preg_match` แบบ `/u` ที่ระบุตำแหน่งเริ่ม ตรวจ UTF-8 ของข้อความทั้งส่วนที่เหลือทุกครั้ง (ราว 6 ไมโครวินาทีต่อครั้งที่ข้อความ 11.7 KB และเพิ่มตามความยาว) PHP ข้ามการตรวจนี้ได้เมื่อสตริงเคยถูก match สำเร็จที่ตำแหน่ง 0 โค้ดเดิมได้ประโยชน์นี้โดยบังเอิญจากการเรียก regex คำย่อที่ตำแหน่งแรก พอผมเพิ่มเงื่อนไขข้ามการเรียก regex คำย่อ ข้อนี้หายไปและบรรทัดยาวช้าลงเป็นกำลังสอง จึงเพิ่ม `preg_match('//u', $text)` หนึ่งครั้งหลังสร้างข้อความ พร้อมคอมเมนต์ ถ้ามีคนเอาออก ตัวเลขบรรทัดยาวจะแย่ลงมาก
- **Go:** `regexp` ของ Go ไม่มี DFA และใช้ backtracker เฉพาะอินพุตสั้น จึงส่งให้ regex เห็นแค่หน้าต่าง 16 ตัวอักษร (รูปแบบที่ยาวที่สุดคือ 11) แล้วใช้ตัวอักษรหลังจากข้อความจริงตัดสินต่อ และแยก regex ตามตัวอักษรแรกของคลัสเตอร์ (ลำดับทางเลือกเหมือนเดิม) มี test เทียบ `TCCPosArray` กับเวอร์ชันเดิมที่ไม่ใช้หน้าต่างบนสตริงสุ่ม 100,000 ชุด (`go/tcc_test.go`)
- **Java:** `substring` ต่อตำแหน่งทั้งใน `ThaiViterbiTokenizer` และ `ThaiTCC` ถูกแทนด้วย `Matcher.region()` (รูปแบบทั้งหมดขึ้นต้นด้วย `^` จึงได้ผลเดียวกับการจับที่ส่วนท้ายของข้อความ)
- **TypeScript:** การดำเนินการระดับบิตของ JS เป็น 32 บิต คำหน้าที่ 43 คำจึงใช้ mask สองตัว

### ที่ยังไม่ได้ทำ

- ข้อ 0 ของแผน (ใส่โปรแกรมวัดไว้ใน `tools/`) โปรแกรมวัดยังอยู่นอก repo
- ไม่ได้ build ใหม่/ปล่อยเวอร์ชัน (Python wheel, wasm/Typst ยังเป็นของเดิม และยังไม่ได้วัดขนาด wasm)
- ไม่ได้รัน parity test ข้ามภาษาด้วย LST20 ที่ทีมใช้ (ตรวจแต่ละภาษากับผลก่อนแก้ของตัวเองบนข้อความข่าวและข้อความสุ่มแทน)
- ไม่ได้เพิ่ม test ป้องกันการกลับมาช้าของบรรทัดยาวใน Java และ PHP เพราะ test ที่อิงเวลาไม่เสถียร

## แผน (เดิม)

หลักการเดียวกับ Rust: ผลลัพธ์ต้องเหมือนเดิมทุก token ทำทีละเรื่องแล้ววัดแต่ละเรื่อง ลำดับตามผลที่คาดว่าคุ้ม:

### 0. เตรียมเครื่องมือวัด
- ใส่โปรแกรมวัดและตัวเปรียบเทียบผลลัพธ์ไว้ใน `tools/` (รับ path ของข้อความเป็นอาร์กิวเมนต์ ไม่มีข้อมูลอยู่ใน repo) ให้รันซ้ำได้ทุกภาษา
- ก่อนแก้แต่ละภาษา เก็บผลลัพธ์ก่อนแก้ (ไฟล์ dump) จาก commit ปัจจุบันของภาษานั้นไว้เป็นข้อมูลอ้างอิง

### 1. PHP (ได้มากที่สุด)
- สร้างตัวตรวจคำหน้าที่ใน OOV edge ใหม่โดยคำนวณตำแหน่งที่คำหน้าที่เริ่มและจบครั้งเดียวต่อข้อความ (แทนที่การเทียบ 43 คำต่อ edge) ที่ประมาณ 60% ของเวลาคาดว่าได้ 2.5 เท่าขึ้นไป
- ตัด `preg_match` ต่อตัวอักษรใน `isThai` และ OOV char class ด้วยการเช็กไบต์ (ผลเหมือนเดิมเพราะบล็อกไทย U+0E00-0E7F เป็น `E0 B8/B9 xx` ใน UTF-8) และเลิกสร้างสตริงต่อ edge (เก็บเฉพาะ `from` ตัดคำตอนย้อนกลับ)
- ทดสอบด้วย `phpunit` เดิมและเทียบผลลัพธ์ชุด A, B, C ก่อน/หลัง

### 2. Java (ปลั๊กอิน OpenSearch, repo `opensearch-analysis-thaibreak`)
- แก้ `substring` ต่อตำแหน่งเป็น `Matcher.region()` / `regionMatches` เพื่อให้เวลาเป็นเส้นตรงตามความยาวบรรทัด (ผลเหมือนเดิมแน่นอน) ลำดับสูงสุดเพราะเป็นข้อบกพร่องด้านการขยายขนาด ไม่ใช่แค่ความเร็วคงที่
- ตามด้วยตัวตรวจคำหน้าที่แบบบิตมาสก์ และเลิกสร้าง `String` ต่อ edge
- ต้องรันชุดทดสอบของปลั๊กอิน (128 test) และเทียบผลลัพธ์ด้วยพจนานุกรมของปลั๊กอินเอง ต้องปล่อยเป็นเวอร์ชันของปลั๊กอิน (ไม่เปลี่ยนผลลัพธ์ จึงไม่ต้อง reindex)

### 3. Go
- ตัวตรวจคำหน้าที่แบบบิตมาสก์ (~30% ของเวลา) และเลิกสร้างสตริงต่อ edge (`slicerunetostring` ~13%)
- TCC: ข้ามการเรียก lookahead regex เมื่อไม่ได้ขึ้นต้นด้วย `เ` (ทุกรูปแบบขึ้นต้นด้วย `เ`) ก่อน แล้ววัด ถ้า `TCCPosArray` ยังกินเวลามาก ค่อยพิจารณา matcher เขียนเอง ซึ่งเสี่ยงให้ผลเปลี่ยนมากกว่า ต้องทดสอบกับสตริงสุ่มจำนวนมากแบบเดียวกับที่ทำกับ Rust
- คาดว่าได้ประมาณ 2 เท่า

### 4. TypeScript
- ตัวตรวจคำหน้าที่แบบบิตมาสก์, เลิก `slice().join('')` และอ็อบเจ็กต์ edge ต่อตำแหน่ง (ใช้อาร์เรย์ร่วมกัน) ลด GC
- `text.slice(charOffsets[i])` ต่อตำแหน่งเป็น slice ที่ V8 ไม่คัดลอก แต่ทำให้ regex ต้องแปลงโครงสร้างสตริงภายใน ให้วัดก่อนว่าแก้แล้วคุ้มหรือไม่
- คาดว่าได้ 1.5-2 เท่า

### 5. ไม่นำมาใช้ซ้ำ
- `perf-dfa` เป็นของ regex crate ของ Rust โดยเฉพาะ
- แคชสถานะ FST หลังอักษรไทย 1-2 ตัว (รอบที่ 2 ของ Rust) ใช้กับ FST เท่านั้น ภาษาอื่นใช้ DAWG ที่โครงสร้างต่างกัน ให้ profile การค้นพจนานุกรมของแต่ละภาษาหลังแก้ข้อ 1-4 แล้วค่อยตัดสินใจ

## เกณฑ์ผ่านของแต่ละภาษา

1. ผลลัพธ์เหมือนก่อนแก้ทุกบรรทัดบนชุด A, B, C และข้อความเต็ม 1,500 บทความ (เทียบกับ dump ของภาษานั้นเอง)
2. ชุดทดสอบของภาษานั้นผ่านทั้งหมด (`go test`, `npm test`, `phpunit`, `gradlew test`)
3. วัดซ้ำด้วยโปรแกรมและข้อความเดียวกัน รายงานเทียบกับตารางด้านบน และวัดบรรทัดยาว (ตารางขนาดบรรทัด) สำหรับ Java
4. ถ้าภาษาไหนผลเปลี่ยนแม้บรรทัดเดียว ให้หยุดและหาสาเหตุก่อน ไม่แก้เกณฑ์

## ความเสี่ยง

- การเปลี่ยนที่ผลเหมือนกันบนข้อความจริงอาจต่างบนอินพุตแปลก ๆ จึงให้เทียบกับสตริงสุ่มปนอักษรหลายชนิดด้วย (ชุด C)
- การออกเวอร์ชัน: ไม่เปลี่ยนผลตัดคำ น่าจะเป็น patch release ของแต่ละแพ็กเกจ ตัดสินใจเมื่อแก้เสร็จ
