# ประสิทธิภาพการตัดคำ (Rust)

สถานะ: บันทึกการค้นคว้าและการวัด (2026-10-15) branch `perf/rust-segmentation`

## โจทย์

ความถูกต้องของการตัดคำอยู่ในระดับที่พอใจแล้ว ข้อที่เหลือ (OOV และคำกำกวม) ต้องใช้เทคนิคที่มีต้นทุนสูงขึ้นมาก จึงมุ่งเพิ่มความเร็วโดยให้ผลการแบ่งคำเหมือนเดิมทุกตัวอักษร (หรือเปลี่ยนน้อยมาก)

## สิ่งที่ค้นจากเว็บ

ผลการค้นยังกว้างและไม่ได้ช่วยระบุคอขวดของโค้ดนี้โดยตรง เป็นเพียงบริบท:

- ผลค้นสรุปว่า double-array trie เร็วกว่า linked trie สำหรับ dictionary matching และการตัดคำที่ไม่ใช้ออก (WUF) ช่วยลดการค้นหา ([ResearchGate: Research on Dictionary-Based Word Segmentation Algorithms Using Trie Structure](https://www.researchgate.net/publication/392773976_Research_on_Dictionary-Based_Word_Segmentation_Algorithms_Using_Trie_Structure)) ยังไม่ได้อ่านต้นฉบับ
- Double-array Aho-Corasick ([arXiv:2207.13870](https://arxiv.org/pdf/2207.13870)) เป็นงานคนละปัญหากับ Viterbi ของเรา
- ผลค้นมีการเร่ง Viterbi บน GPU ด้วย ซึ่งไม่เหมาะกับไลบรารีที่ต้องรันบน CPU ทั่วไป

แนวทางที่ได้ผลจริงมาจากการวัดและอ่านโค้ด ไม่ได้มาจากเอกสารเหล่านี้

## วิธีวัด

- ข้อความ: บทความข่าว 1,500 เรื่องจากคลังในเครื่อง (ประมาณ 8.04 ล้านตัวอักษร) ไม่ได้ commit ลง repo
- build: `--release` พร้อม LTO และ `codegen-units = 1` เหมือน `rust/Cargo.toml`
- ใช้ `ThaiTrie::embedded()` และ `Tokenizer::new(trie, None)`, รัน 3 รอบ เอาเวลาดีที่สุด
- ตรวจผลด้วย FNV hash ของ token ทั้งหมด ถ้า hash ตรงกับเดิม (`389dea6213bc8526`) ถือว่าผลเหมือนกัน
- ไม่มี perf/flamegraph ในเครื่อง จึงใช้การ ablation (ปิดส่วนหนึ่งแล้ววัดเวลาที่ลด) และการวัดฟังก์ชันย่อยโดยตรง

## สาเหตุหลักของความช้า

`rust/Cargo.toml` ตั้ง `default-features = false` ให้ `regex` และไม่ได้เปิด feature `perf-*` ใด ๆ ทำให้ regex ไม่มี lazy DFA และต้องใช้ engine ที่ช้ากว่ามาก `tcc_pos_array` เรียก regex แบบ `^(?:...)` ทุกคลัสเตอร์ จึงกินเวลาเกือบทั้งหมด

การเปิด `perf-dfa` (ไม่ใช่ `perf` ทั้งชุด ซึ่งให้ผลใกล้เคียงกัน) แก้ปัญหานี้ได้โดยไม่เปลี่ยนผลลัพธ์

## การเปลี่ยนแปลงใน branch นี้

- `rust/Cargo.toml`: เพิ่ม feature `perf-dfa` ให้ `regex`
- `rust/src/tcc.rs`:
  - แทน `HashMap<usize, usize>` (byte → char index) ด้วย `Vec` ที่ index ด้วย byte offset
  - เรียก `TCC_LOOKAHEAD_REGEX` เฉพาะเมื่อข้อความขึ้นต้นด้วย `เ` เพราะทุกรูปแบบในนั้นขึ้นต้นด้วย `เ`
- `rust/src/tokenizer.rs`:
  - DP ไม่เก็บ `String` ของทุกขอบ เพราะขอบทุกเส้นคือ `chars[i..j]` จึงเก็บเฉพาะ `from` และ `is_unk` แล้วตัดสตริงตอนย้อนกลับ (traceback)
  - bigram ยังสร้างสตริงเมื่อมี model เท่านั้น ตามพฤติกรรมเดิม
  - ตรวจคำหน้าที่ใน OOV ด้วย bitmask ที่คำนวณครั้งเดียวต่อข้อความ (`function_word_positions`) แทนการเทียบสตริงทุกคลัสเตอร์ เงื่อนไขเหมือนเดิมทุกข้อ

## การตรวจสอบ

- `cargo test` ใน `rust/` ผ่านทั้งหมด และ `cargo build --release` ไม่มี warning
- hash ของผลการตัดคำบนข้อความ 8.04 ล้านตัวอักษรเท่ากับเดิมทุกขั้นตอน
- ยังไม่ได้รันการวัดความถูกต้องบน LST20 ใหม่ เพราะผลลัพธ์ที่เหมือนเดิมทุก token บนข้อความจำนวนมากหมายความว่าค่า F1 ไม่เปลี่ยน

## ข้อควรระวัง

- `perf-dfa` เพิ่มขนาดโค้ด regex ยังไม่ได้วัดขนาดของ binary ใน wasm (`rust/src/wasm.rs`) และ Typst plugin ต้องตรวจก่อนปล่อยเวอร์ชัน
- ภาษาอื่น (Go, TS, PHP, Java) ยังใช้อัลกอริทึมเดิมและยังช้าเท่าเดิม ผลลัพธ์ยังตรงกันตามหลักการ แต่ยังไม่ได้ตรวจด้วย parity test หลังการเปลี่ยนนี้
- การอ้างอิงว่า `tcc_pos_array` ไม่ panic พึ่งการที่ regex คืนขอบเขตที่เป็น UTF-8 ที่ถูกต้องเสมอ (ทุกตำแหน่งที่ใช้เป็นขอบเขตของ char) ถ้ามีการเปลี่ยน regex ให้ตรวจส่วนนี้ใหม่

## สิ่งที่ยังทำได้

- เวลาที่เหลือราว 2 วินาทีอยู่ที่ DP และการค้นหาใน FST ส่วนที่ยังทำได้คือลด `String` ใน `PrefixMatch` และแคชค่า `ln(normalizer / weight)` ต่อคำ
- ย้ายการเปลี่ยนแปลงแบบเดียวกันไป Go, TS, PHP และ Java หลังตรวจ parity แล้ว
