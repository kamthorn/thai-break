# ประสิทธิภาพการตัดคำ (Rust)

สถานะ: บันทึกการค้นคว้าและการวัด (2026-10-15) branch `perf/rust-segmentation`

## โจทย์

ความถูกต้องของการตัดคำอยู่ในระดับที่พอใจแล้ว ข้อที่เหลือ (OOV และคำกำกวม) ต้องใช้เทคนิคที่มีต้นทุนสูงขึ้นมาก จึงมุ่งเพิ่มความเร็วโดยให้ผลการแบ่งคำเหมือนเดิมทุกตัวอักษร (หรือเปลี่ยนน้อยมาก)

## สิ่งที่ค้นจากเว็บ

ผลการค้นยังกว้างและไม่ได้ช่วยระบุคอขวดของโค้ดนี้โดยตรง เป็นเพียงบริบท:

- ผลค้นสรุปว่า double-array trie เร็วกว่า linked trie สำหรับ dictionary matching และการตัดคำที่ไม่ใช้ออก (WUF) ช่วยลดการค้นหา ([ResearchGate: Research on Dictionary-Based Word Segmentation Algorithms Using Trie Structure](https://www.researchgate.net/publication/392773976_Research_on_Dictionary-Based_Word_Segmentation_Algorithms_Using_Trie_Structure)) ยังไม่ได้อ่านต้นฉบับ
- Double-array Aho-Corasick ([arXiv:2207.13870](https://arxiv.org/pdf/2207.13870)) เป็นงานคนละปัญหากับ Viterbi ของเรา
- ผลค้นมีการเร่ง Viterbi บน GPU ด้วย ซึ่งไม่เหมาะกับไลบรารีที่ต้องรันบน CPU ทั่วไป

แนวทางที่ได้ผลจริงมาจากการวัดและอ่านโค้ด ไม่ได้มาจากเอกสารเหล่านี้

## วิธีวัด

- ข้อความ: บทความข่าว 1,500 เรื่องจากคลังในเครื่อง (ประมาณ 8.04 ล้านตัวอักษร) ไม่ได้ commit ลง repo
- build: `--release` พร้อม LTO และ `codegen-units = 1` เหมือน `rust/Cargo.toml`
- ใช้ `ThaiTrie::embedded()` และ `Tokenizer::new(trie, None)`, รัน 3 รอบ เอาเวลาดีที่สุด
- ตรวจผลด้วย FNV hash ของ token ทั้งหมด ถ้า hash ตรงกับเดิม (`389dea6213bc8526`) ถือว่าผลเหมือนกัน
- ไม่มี perf/flamegraph ในเครื่อง จึงใช้การ ablation (ปิดส่วนหนึ่งแล้ววัดเวลาที่ลด) และการวัดฟังก์ชันย่อยโดยตรง

## สาเหตุหลักของความช้า

`rust/Cargo.toml` ตั้ง `default-features = false` ให้ `regex` และไม่ได้เปิด feature `perf-*` ใด ๆ ทำให้ regex ไม่มี lazy DFA และต้องใช้ engine ที่ช้ากว่ามาก `tcc_pos_array` เรียก regex แบบ `^(?:...)` ทุกคลัสเตอร์ จึงกินเวลาเกือบทั้งหมด

การเปิด `perf-dfa` (ไม่ใช่ `perf` ทั้งชุด ซึ่งให้ผลใกล้เคียงกัน) แก้ปัญหานี้ได้โดยไม่เปลี่ยนผลลัพธ์

## การเปลี่ยนแปลงใน branch นี้

- `rust/Cargo.toml`: เพิ่ม feature `perf-dfa` ให้ `regex`
- `rust/src/tcc.rs`:
  - แทน `HashMap<usize, usize>` (byte → char index) ด้วย `Vec` ที่ index ด้วย byte offset
  - เรียก `TCC_LOOKAHEAD_REGEX` เฉพาะเมื่อข้อความขึ้นต้นด้วย `เ` เพราะทุกรูปแบบในนั้นขึ้นต้นด้วย `เ`
- `rust/src/tokenizer.rs`:
  - DP ไม่เก็บ `String` ของทุกขอบ เพราะขอบทุกเส้นคือ `chars[i..j]` จึงเก็บเฉพาะ `from` และ `is_unk` แล้วตัดสตริงตอนย้อนกลับ (traceback)
  - bigram ยังสร้างสตริงเมื่อมี model เท่านั้น ตามพฤติกรรมเดิม
  - ตรวจคำหน้าที่ใน OOV ด้วย bitmask ที่คำนวณครั้งเดียวต่อข้อความ (`function_word_positions`) แทนการเทียบสตริงทุกคลัสเตอร์ เงื่อนไขเหมือนเดิมทุกข้อ

## การตรวจสอบ

- `cargo test` ใน `rust/` ผ่านทั้งหมด และ `cargo build --release` ไม่มี warning
- hash ของผลการตัดคำบนข้อความ 8.04 ล้านตัวอักษรเท่ากับเดิมทุกขั้นตอน
- ยังไม่ได้รันการวัดความถูกต้องบน LST20 ใหม่ เพราะผลลัพธ์ที่เหมือนเดิมทุก token บนข้อความจำนวนมากหมายความว่าค่า F1 ไม่เปลี่ยน

## ข้อควรระวัง

- `perf-dfa` เพิ่มขนาดโค้ด regex ยังไม่ได้วัดขนาดของ binary ใน wasm (`rust/src/wasm.rs`) และ Typst plugin ต้องตรวจก่อนปล่อยเวอร์ชัน
- ภาษาอื่น (Go, TS, PHP, Java) ยังใช้อัลกอริทึมเดิมและยังช้าเท่าเดิม ผลลัพธ์ยังตรงกันตามหลักการ แต่ยังไม่ได้ตรวจด้วย parity test หลังการเปลี่ยนนี้
- การอ้างอิงว่า `tcc_pos_array` ไม่ panic พึ่งการที่ regex คืนขอบเขตที่เป็น UTF-8 ที่ถูกต้องเสมอ (ทุกตำแหน่งที่ใช้เป็นขอบเขตของ char) ถ้ามีการเปลี่ยน regex ให้ตรวจส่วนนี้ใหม่

## รอบที่ 2: profile หลังแก้ regex (2026-10-15)

### วิธีวัด

ข้อความข่าวชุดเดิมไม่อยู่ในเครื่องที่ใช้รอบนี้ และ HuggingFace ถูกบล็อก จึงใช้ข้อความที่เปิดเผยแทน (ไม่ได้ commit ลง repo):

- ข่าว: `model/1.5/data.txt` ของ [wannaphong/thai-ner](https://github.com/wannaphong/thai-ner) ลบแท็ก NE และ URL ออก 6,387 บรรทัด 1.05 ล้านตัวอักษร
- โซเชียล: `pos/neg/neu/q.txt` ของ [PyThaiNLP/wisesight-sentiment](https://github.com/PyThaiNLP/wisesight-sentiment) 26,737 บรรทัด 2.40 ล้านตัวอักษร
- ความถูกต้อง: Wisesight-1000 (CC0) เทียบ gold แบบช่วงคำ (คนละวิธีนับกับตารางใน README ตัวเลขใช้เทียบก่อน/หลังเท่านั้น)

ตัดคำทีละบรรทัดด้วย `Tokenizer::new(ThaiTrie::embedded()?, None)` และ `tokenize(line, true)` เทียบ token ทุกตัวกับ build ของ commit ก่อนหน้า (`7efd467`) ด้วย `cmp` ของไฟล์ผลลัพธ์ทั้งไฟล์ เวลาบนเครื่องนี้แกว่งมาก (โค้ดเดียวกันวัดได้ 0.38–0.51 วินาที) จึงใช้จำนวนคำสั่ง (instruction count) จาก callgrind บนข้อความย่อย (800 บรรทัดข่าว, 3,000 บรรทัดโซเชียล) เป็นตัวชี้วัดหลัก และใช้เวลาที่ดีที่สุดจาก 7 รอบประกอบ

### สัดส่วนเวลา (ablation บนข่าว 800 บรรทัด)

| ส่วน | สัดส่วนโดยประมาณ |
|---|---|
| ค้นคำในพจนานุกรม (FST prefix walk + ขอบของคำ) | ~48% |
| `function_word_positions` (ก่อนแก้) | ~35% ของทั้งหมดก่อนแก้ |
| TCC | ~8% |

| ลำดับตัวอักษรที่สะกดเป็นชื่อ (เอทีเอ็ม) | ~3% |

### การเปลี่ยนแปลง (ผลลัพธ์เหมือนเดิมทุก token)

- `function_word_positions` เดิมเทียบคำหน้าที่ 43 คำกับทุกตำแหน่ง และถอดรหัส UTF-8 ของคำใหม่ทุกครั้ง แก้ให้เทียบเฉพาะคำที่ขึ้นต้นด้วยอักษรตัวเดียวกับตำแหน่งนั้น
- เรียก regex คำย่อเฉพาะเมื่อมี `.` ภายใน 4 ตัวอักษรถัดไป (รูปแบบคำย่อยาวไม่เกิน 4 ตัวอักษรก่อน `.` แรก จึงไม่มีทางจับได้ถ้าไม่มี `.`)
- ลำดับชื่อตัวอักษร: เทียบชื่อเฉพาะเมื่ออักษรตัวแรกตรงกัน
- `ThaiTrie::prefix_ends_from_chars` คืนเฉพาะ `(end, weight)` ลง buffer ที่ใช้ซ้ำ ไม่สร้าง `String` ต่อคำที่พบ (`prefixes_from_chars` ยังอยู่และให้ผลเหมือนเดิม มี test เทียบกันทุกตำแหน่ง)
- FST ของ Thai ใช้ 3 node ต่อ 1 ตัวอักษร (UTF-8 3 ไบต์) และการค้นจากแต่ละตำแหน่งเดินเฉลี่ย 2.9 ตัวอักษร โดย 58% ของก้าวอยู่ในสองตัวอักษรแรก จึงเก็บสถานะ FST หลังอักษรไทย 1–2 ตัวแรกไว้ในตาราง (`ThaiPrefixes`: index `u16` 128 + 128×128 ช่อง และสถานะ ~1,100 ตัว รวมประมาณ 60 KB) สร้างตอนค้นครั้งแรกและแชร์ระหว่าง clone ด้วย `Arc<OnceLock>`
- น้ำหนักที่ตั้งด้วย `set_weight` เขียนลง `weights` ตรง ๆ แทน `HashMap<u64, f64>` ที่ต้อง hash (SipHash) ทุกครั้งที่พบคำ เพราะน้ำหนักเริ่มต้น 3,000 คำถูกใส่ผ่าน `set_weight`
- `tcc_pos_array` ไม่สร้างตาราง byte → char index (8 ไบต์ต่อไบต์ของข้อความ) แต่นับตัวอักษรของแต่ละคลัสเตอร์แทน

## รอบที่ 3: TCC แบบ DFA และ boundaries ที่ไม่สร้างสตริง (2026-10-18)

### โจทย์

เทียบกับ libthai (`libthai.so.0.3.1`, `th_brk_wc_find_breaks`) ผ่าน C API บนเครื่องเดียวกัน thai-break ช้ากว่า 1.3–1.6 เท่า จึง profile เพื่อหาส่วนที่ต่าง

### วิธีวัด

- เครื่อง: Intel i7-14700F แกนเดียว (`taskset -c 2`), โปรแกรม C คอมไพล์ด้วย gcc 14 `-O2` เรียก `thaibreak_boundaries` และ `thaibreak_tokenize` ด้วย `data/words.fst`
- ข้อความ (ไม่ได้ commit): ย่อหน้าข่าว Prachathai 5,000 ย่อหน้า (1.84 ล้านตัวอักษร), ประโยคสั้น 2,299 ประโยค (82,000 ตัวอักษร), ข้อความไทยล้วนยาว 100,000 ตัวอักษร
- เวลา: ดีที่สุดจาก 15 รอบ รันไลบรารีเก่าและใหม่สลับกัน
- profile: ไม่มี perf และ valgrind จึงใช้ `SIGPROF` เก็บ program counter และไล่ frame pointer (build ด้วย `-C force-frame-pointers=yes` และ line table) แล้วแปลงด้วย `addr2line` ได้ราว 10,000 ตัวอย่างต่อครั้ง
- ความถูกต้อง: `cmp` ผล token และ boundaries ของทุกบรรทัดกับ build ก่อนหน้า บนย่อหน้าข่าว 65,014 ย่อหน้า, ประโยคสั้น และสตริงสุ่ม 150,000 บรรทัด (ทั้งบล็อกไทย, พยัญชนะกับสระ, ชิ้นข่าวที่สุ่มแก้ และตัวอักษรละตินปน)

### สัดส่วนเวลาก่อนแก้ (ย่อหน้าข่าว, 149 ns ต่อตัวอักษร)

| ส่วน | สัดส่วน |
|---|---|
| ลูป Viterbi, edge OOV และการสร้าง String/Vec ใน `segment` | 31% |
| ค้นพจนานุกรม (FST) | 26% |
| TCC (regex DFA ของ crate `regex`) | 21% |
| malloc/free/memcpy | 12% |
| BreakIterator และ FFI | 3% |
| mask คำหน้าที่ | 3% |

libthai ใช้ 99 ns ต่อตัวอักษร ครึ่งหนึ่งอยู่ใน libdatrie (เดิน trie) ซึ่งช้ากว่าการค้น FST ของเรา ส่วนที่ต่างจึงอยู่ที่ TCC และการจองหน่วยความจำ

### การเปลี่ยนแปลง (ผลลัพธ์เหมือนเดิมทุก byte)

- **TCC:** compile กฎชุดเดิมเป็น DFA แบบ leftmost-first ตอนใช้ครั้งแรก
  - วิธีสร้าง: แปลงกฎเป็น NFA แล้วทำ subset construction บนรายการ thread ที่เรียงตามลำดับความสำคัญ และตัด thread ที่อยู่หลัง Match ทิ้ง ซึ่งเป็นวิธีเดียวกับที่ regex แบบ leftmost-first ทำ จึงได้ match เดียวกับ alternation ของ regex เดิม
  - DFA ทำงานทีละตัวอักษรบนกลุ่มตัวอักษร (equivalence class) แทนทีละไบต์ UTF-8
  - ขนาด: 157 สถานะ 29 กลุ่ม ใช้ 9 KB สร้างเสร็จใน 0.7 ms
  - กฎยังเขียนเป็นสตริงชุดเดิม และ test ยังสร้าง regex จากกฎเหล่านั้นเป็นตัวอ้างอิง เทียบบนสตริงสุ่ม 200,000 ชุด
- **`segment` คืนช่วงตำแหน่งของคำ:** `Tokenizer::boundaries` (ใช้ใน `BreakIterator` และ `thaibreak_boundaries`) คำนวณ offset จากช่วงตำแหน่งโดยไม่สร้าง `String` ของแต่ละคำ ถ้าข้อความไม่ต้อง normalize `segment` จะใช้ข้อความเดิมแทนการสร้าง `String` ใหม่
- **relax edge ทันทีที่พบ:** ไม่ต้องเก็บ edge ไว้ใน Vec ลำดับการ relax เหมือนเดิม และขั้นตอนหา edge ไม่ได้อ่านค่า dp ของตำแหน่งหลัง i จึงได้ผลเดิมแม้กรณีต้นทุนเท่ากัน
- **ค้นชื่อตัวอักษรละติน:** index ตามอักษรตัวแรก แบบเดียวกับคำหน้าที่

### สัดส่วนเวลาหลังแก้ (110 ns ต่อตัวอักษร)

ลูป Viterbi และ edge OOV 36%, ค้น FST 33%, TCC 10%, malloc/free 8%, mask คำหน้าที่ 5% ส่วนที่เหลือของช่องว่างกับ libthai (ราว 6–14%) คือ Viterbi และ edge OOV ซึ่งเป็นงานที่ libthai ไม่ได้ทำ และเป็นที่มาของความแม่นยำที่สูงกว่า

## สิ่งที่ยังทำได้

- ส่วนที่เหลือราว 13% อยู่ใน FST หลังสองตัวอักษรแรก ถ้ายอมรับหน่วยความจำ ~1.2 MB ได้ (เช่นใช้ในเซิร์ฟเวอร์) trie ระดับตัวอักษรเป็นตัวเลือกแบบ opt-in ได้ โค้ดทดลองอยู่ในประวัติการทำงาน ไม่ได้ commit
- ~~TCC ด้วย DFA~~ ทำแล้วในรอบที่ 3 (DFA ที่สร้างเองจากกฎ ไม่ต้องพึ่ง `regex-automata` โดยตรง)
- การจองหน่วยความจำต่อการเรียก: รอบที่ 3 ตัด `String` ของคำในเส้นทาง boundaries และ `String` ของข้อความใน `segment` แล้ว ยังเหลือ Vec ต่อการเรียกราว 12 ตัว (malloc/free ราว 8%) ถ้าจะลดอีกต้องใช้ buffer ต่อเธรด
- ย้ายการเปลี่ยนแปลงแบบเดียวกันไป Go, TS, PHP และ Java ดู `docs/performance-ports.md`
